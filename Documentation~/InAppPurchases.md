# Внутриигровые покупки

`IInAppProvider` наследует `IUniWebFeature` и `IDisposable`. Контракт, базовый класс и безопасная заглушка находятся в `Runtime/Features/InAppPurchases`. Реализованы `GamePushInAppProvider`, `PluginYG2InAppProvider` и ограниченный клиентский `VKGamesInAppProvider`.

## Контракт

| Член | Назначение |
| --- | --- |
| `IsSupported` | Поддерживаются ли покупки текущим провайдером и площадкой |
| `IsReady` | Можно ли обращаться к покупкам сейчас |
| `IsBusy` | Ожидается ли результат операции покупки, консумации или подписки |
| `IsSubscriptionsSupported` | Доступны ли операции подписки |
| `ConsumeMode` | Консумация по ID товара, токену или ID конкретной покупки, автоматическая консумация SDK либо отсутствие поддержки |
| `Products`, `Purchases` | Доступные только для чтения снимки каталога и покупок |
| `FetchProducts` | Получить каталог и обновить `Products` |
| `FetchPurchases` | Получить принадлежащие игроку/неизрасходованные покупки и обновить `Purchases` |
| `RefreshProducts`, `RefreshPurchases` | Явно запросить обновление у платформы; `Unsupported`, если SDK не предоставляет такой операции |
| `ProductsChanged`, `PurchasesChanged` | События изменения соответствующих неизменяемых снимков |
| `TryGetProduct`, `HasPurchase` | Найти товар и проверить владение по последнему снимку |
| `Purchase` | Запустить покупку и получить запись с её состоянием; `Pending` не подтверждает оплату |
| `Consume` | Подтвердить обработку расходуемой покупки |
| `Subscribe`, `Unsubscribe` | Оформить подписку или отключить её продление |
| `Dispose` | Освободить подписки и завершить ожидающий callback ошибкой `Disposed` |

Методы имеют отдельные callbacks успеха и ошибки. Результат может прийти синхронно. Заглушка завершает операции ошибкой `Unsupported`, никогда не сообщает успешную оплату и не выдаёт награды. Объекты моделей неизменяемы; обновление SDK не изменяет ранее полученный снимок.

## Явное обновление и события

`Fetch*` сохраняют прежнюю семантику адаптеров: могут читать уже загруженный
снимок SDK. `Refresh*` — отдельный запрос обновления платформенных данных;
базовая реализация честно возвращает `Unsupported`, а не выдаёт чтение кэша
за сетевую синхронизацию. У текущих GamePush/PluginYG2 адаптеров force-refresh
пока не реализован. Для своего SDK или серверного магазина переопределите эти методы.

События вызываются только при изменении содержимого снимка, после завершения
операции и её callback. Одинаковые данные не порождают повторных событий.
В наследнике базового класса обновляйте снимки через `SetProducts` / `SetPurchases`,
а после освобождения занятой операции вызывайте защищённый `NotifyChanges`.
Исключение подписчика логируется и не блокирует остальных. `Dispose` снимает подписчиков.

Режим `InAppConsumeMode.PurchaseId` означает адресную консумацию
`InAppPurchase.PurchaseId`. Он добавлен в конец enum с сохранением прежних значений.
Общий контракт уже передаёт модель покупки в `Consume`; новая перегрузка не нужна.
Поддержку режима объявляет конкретный адаптер: текущий GamePush остаётся `ProductId`,
PluginYG2 — `Automatic`, VK — `None`.

## Инициализация и доступ

Static Bootstrapper регистрирует заглушку, затем заменяет её адаптером выбранного SDK. Доступ: `UniWebBridge.InApps`.

VContainer регистрирует `IInAppProvider` по тому же принципу Last-in Wins. Получите его через DI после `builder.RegisterUniWeb()`. Для кастомного провайдера зарегистрируйте свою реализацию после этого вызова.

Ручная инициализация Static API:

```csharp
UniWebBridge.Initialize(ads: myAds, inApps: myInApps);
```

Существующий `Initialize(ads)` продолжает работать и устанавливает заглушку покупок. Замена `InApps` освобождает прежний провайдер; повторная передача того же экземпляра его не уничтожает.

Создание провайдера не означает, что платформенный SDK уже готов. До готовности SDK GamePush флаги поддержки/готовности возвращают `false`, а операции — `NotReady`. Проверяйте `IsReady` при открытии магазина и повторяйте запрос после инициализации платформы. При недоступных покупках UI можно скрыть через `IsSupported`.

## Каталог и восстановление

В `InAppProduct` доступны ID, название, описание, изображения, числовая цена, текст цены, код/символ/изображение валюты и тип товара. Числовая цена nullable: отсутствие данных не превращается в бесплатный товар. Для подписок предусмотрены длительность и пробный период в днях.

`InAppPurchase` отделён от каталога: он содержит ID товара, необязательные ID/токен покупки, payload, состояние, даты и nullable-флаг автопродления. Отсутствующий ID транзакции остаётся пустым. ID товара не используется как поддельный ID транзакции.

После запуска загрузите `FetchPurchases`. Это восстановление постоянных прав и поиск покупок, которые не успели обработаться в предыдущем запуске, а не полная история платежей. Для постоянного права используйте `HasPurchase` после загрузки снимка. Pending/cancelled-записи и записи с истёкшей датой не подтверждают владение. Проверка даты на клиенте служит удобству UI и не заменяет серверную проверку права.

## Выдача и консумация

Для расходуемого товара при ручной консумации (`ProductId` / `PurchaseToken` / `PurchaseId`) последовательность такая. Режим `Automatic` описан отдельно ниже: в нём SDK запускает консумацию до игрового сохранения.

1. Получить подтверждённую покупку.
2. Начислить награду и надёжно сохранить прогресс.
3. Вызвать `Consume`.
4. При ошибке консумации повторить обработку через восстановление покупок, не начисляя награду второй раз.

Для постоянного товара консумация не вызывается. Выбор награды, классификация товаров и сохранение относятся к игровой логике. Пакет ничего не начисляет автоматически.

Пример связывания с игровым сохранением:

```csharp
using System;

namespace UniWebKit
{
    public static class InAppFlowExample
    {
        public static void BuyConsumable(IInAppProvider store, string productId,
            Action<InAppPurchase, Action> grantAndPersist,
            Action<InAppError> onError)
        {
            store.Purchase(productId, purchase =>
            {
                // Pending (например, окно заказа VK) ещё не подтверждает оплату.
                if (purchase.State != InAppPurchaseState.Purchased) return;
                // grantAndPersist вызывает done только после успешного сохранения.
                grantAndPersist(purchase, () =>
                {
                    if (store.ConsumeMode != InAppConsumeMode.Automatic)
                        store.Consume(purchase, onError: onError);
                });
            }, onError);
        }
    }
}
```

Повторяемая обработка должна быть идемпотентной: сохраняйте идентификатор обработанной транзакции вместе с наградой, если платформа его предоставляет. Если SDK не предоставляет уникального ID, клиентский мост не может гарантировать строго однократную выдачу после сбоя. Для строгой гарантии нужна соответствующая игровая/серверная схема обработки.

## Особенности адаптера GamePush

- `InAppProduct.Id` использует тег, а `PlatformId` — числовой ID. Поиск и callbacks принимают оба варианта.
- `FetchProducts`/`FetchPurchases` читают данные, уже загруженные SDK после его инициализации, через `GetProducts`/`GetPurchases`. Это не отдельные запросы принудительной серверной синхронизации.
- SDK не сообщает, является ли обычный товар расходуемым: его тип остаётся `Unknown`. Классификация хранится в игровом каталоге. Подписки распознаются явно.
- SDK принимает консумацию по товару, поэтому `ConsumeMode == ProductId`. Передача модели покупки не превращает такую консумацию в адресную операцию над конкретным receipt.
- Unity API не сообщает отдельную причину отмены платежа: общий отказ возвращается как `Failed`, без выдуманного `Cancelled`.
- Операции сериализованы между экземплярами адаптера, поскольку глобальные ошибки SDK не содержат ID запроса. Не смешивайте прямые транзакционные вызовы SDK с вызовами через UniWebKit.
- На успехе/ошибке снимаются обе одноразовые подписки до вызова клиентского callback. Если провайдер освобождён во время оплаты, он и его клиентские callbacks отсоединяются. Небольшой независимый обработчик ждёт поздний результат SDK, удерживая `IsBusy`, чтобы он не попал следующей покупке; затем также отписывается. Начало новой игровой сессии сбрасывает этот обработчик. Автоматических повторов оплаты и тайм-аутов, разрешающих вторую покупку с неизвестным результатом первой, нет.
- Успешная оплата остаётся успешной при последующей ошибке чтения инвентаря. Недостающие метаданные восстанавливаются отдельной загрузкой покупок.
- `Unsubscribe` отключает продление. Доступ может сохраняться до `ExpiresAt`; `IsAutoRenewing == false` сам по себе не означает утрату права.

## Особенности адаптера PluginYG2

- Код обёрнут в `UNIWEB_PLUGIN_YG2` и вызывает общий API `YG2`, не привязываясь к Yandex API. Выбор конкретной площадки остаётся за PluginYG2. Без `Payments_yg` класс сохраняет безопасное неподдерживаемое поведение.
- Готовность определяется готовностью SDK и наличием непустого платёжного каталога. SDK не предоставляет отдельного универсального флага доступности платежей: до загрузки каталога `IsReady`/`IsSupported` равны `false`.
- Каталог сохраняет предоставленные SDK текст цены и изображение валюты. `FetchProducts`/`FetchPurchases` читают снимок `YG2.purchases`, не инициируя повторную загрузку или консумацию. В список покупок попадают только элементы с `consumed == false`.
- `Purchase` использует `YG2.BuyPayments`. **SDK сам запускает консумацию до `onPurchaseSuccess`**, поэтому `ConsumeMode == Automatic`. После обычной покупки повторно вызывать `Consume` не нужно. Гарантировать сохранение награды до консумации через этот API нельзя.
- `Consume` предназначен для ранее необработанных покупок из `FetchPurchases` и вызывает `YG2.ConsumePurchaseByID(id, true)`. Завершение соответствует уведомлению SDK; отдельного надёжного события подтверждения/ошибки серверной консумации PluginYG2 не предоставляет. Не смешивайте такие вызовы с прямыми вызовами платежей SDK.
- SDK возвращает только ID товара и признак `consumed`: уникальный ID транзакции, purchase token, количество отдельных покупок одного товара и история постоянных прав недоступны. Пустые ID транзакции/токена не заменяются ID товара. Игровые награды и постоянные права должны сохраняться собственной системой прогресса; полностью надёжную двухфазную обработку этот адаптер не заявляет.
- Подписки остаются неподдерживаемыми и завершаются через безопасные базовые методы. Ошибка платежа не выдаётся за достоверную отмену игроком.
- Подписки на `onPurchaseSuccess`/`onPurchaseFailed` одноразовые, результат фильтруется по ID. Между экземплярами действует общий запрет параллельных операций. При уничтожении провайдера независимый обработчик дожидается позднего результата, не удерживая провайдер и callbacks игры.
- В Editor используется штатная симуляция покупки PluginYG2. Консумация имитируется локально в памяти, поскольку метод консумации самого SDK в Editor ничего не делает. Файлы SDK и его настройки не изменяются.
## VK Games / VK Bridge

Клиентский SDK открывает окно через `VKWebAppShowOrderBox`. У этого API нет
клиентских методов каталога, списка покупок или консумации. Поэтому `Fetch*`,
`Refresh*`, `Consume` возвращают `Unsupported`; снимки остаются пустыми, а
`ConsumeMode == None`. Подписки текущим адаптером не реализованы, хотя у VK есть
отдельный диалог подписки: для его полного жизненного цикла также нужен backend.

`Purchase` принимает ID товара, настроенного в обработчике платежей игры.
Ответ `chargeable` с реальным `order_id` возвращается как `InAppPurchaseState.Pending`.
Callback операции завершился, но это **не выдача товара и не подтверждённая оплата**.
Награждать игрока по этому callback нельзя: состояние `Purchased` клиент не выдумывает.
Отмена с явным `status == cancel` возвращает `Cancelled`; ошибки не маскируются под отмену.
Отсутствующий ID заказа не заменяется ID товара.

Для каталога, инвентаря, выдачи товара и проверки заказов нужен собственный сервер,
обрабатывающий [платёжные callbacks VK](https://github.com/VKCOM/vk-direct-games-example#внутриигровые-покупки).
Такой магазин можно реализовать отдельным `IInAppProvider`, не меняя игровую логику.
Покупки сериализованы между экземплярами и не пересекаются с показом рекламы.
После `Dispose` SDK может ещё завершить окно: слот удерживается до ответа,
а игровые callbacks отсоединяются. Синтетического таймаута, разрешающего повторную
оплату при неизвестном результате первой, нет.

Старый экспериментальный JS-export `UniWebVK_PurchaseItem` не умеет выразить
`Pending` и теперь возвращает ошибку с указанием нового request API, не открывая
платёжное окно. C#-провайдер использует запросы с ID через `UniWebVK_Request`.

## Исследованные реализации

| Источник | Что влияет на общий контракт |
| --- | --- |
| [GamePush Payments](https://docs.gamepush.com/docs/purchases/payments/) и установленный Unity SDK | Каталог, владение, ID/теги, отдельная консумация и подтверждение результата |
| [GamePush Subscriptions](https://docs.gamepush.com/docs/purchases/subscriptions/) | Дополнительная возможность подписок, период действия, продление и его отмена |
| [Yandex Games](https://yandex.ru/dev/games/doc/ru/sdk/sdk-purchases) | Консумация по токену, отдельные каталог и покупки, восстановление после сбоя |
| Установленный PluginYG2, модуль `Payments` | Его C#-обёртка возвращает ID товара и автоматически запускает консумацию; точного токена/отдельного подтверждения консумации в этом API нет. Адаптер явно возвращает режим `Automatic`, не обещая двухфазную обработку |
| [CrazyGames / Xsolla](https://docs.crazygames.com/sdk/in-game-purchases/) | Закрытие платёжного окна не подтверждает оплату; права восстанавливаются по данным инвентаря/проверенного заказа |

Интерфейс не раскрывает типы SDK. Для неподдерживаемой площадки остаётся `UnsupportedInAppProvider`. Работа со сторонними SDK и игровая папка `Assets` этим модулем не изменяются.

## Проверки

Контракт и адаптер проверены с управляемым двойником SDK без обращения к платёжным сервисам. Исходники также проверены компилятором Unity против установленных библиотек GamePush/VContainer в вариантах GamePush/без платформы и Static/VContainer.

Реальную оплату, восстановление после перезагрузки браузера и WebGL/IL2CPP необходимо проверять в тестовом окружении площадки до выпуска игры.
